# jev-browse

MCP server + CLI that hands browser goals to TypeSafe Jev (one `/v1/systemone` request per step) and returns a short summary to the calling agent.

## Commands
- `pnpm test`: offline unit tests (vitest), no key needed
- `pnpm typecheck` / `pnpm build` (emits `dist/`, copies `snapshot.js`)
- `pnpm verify`: live, headless Chrome + real Jev; needs `TYPESAFE_API_KEY` (costs credits, about 30 s). `JEV_MODEL=<profile>` runs it on another model via `OPENROUTER_API_KEY` (also Jev without `TYPESAFE_API_KEY`); `JEV_VERIFY_MIN_CONFIDENCE` overrides the threshold for experiments
- `pnpm verify:langfuse`: sixteen read-only jobs (an AI engineer's flows) in Langfuse's demo project from its home page, 3 runs each, recorded (video + described steps) into one `report.html`. Needs a Chrome signed in to cloud.langfuse.com on a debugging port (`JEV_LANGFUSE_BROWSER`, default `http://127.0.0.1:9333`); `JEV_LANGFUSE_RUNS`, `JEV_LANGFUSE_ONLY` narrow it. A pass needs the page check **and** status `done`
- `pnpm verify:real`: live public sites (Wikipedia, MDN, GitHub, Hacker News, npm, Booking.com, Airbnb, Google Flights), a fresh headless Chrome per run, 5 runs each; `JEV_REAL_RUNS`, `JEV_REAL_ONLY` narrow it. Bot walls are reported apart from failures, judged on the final page by the run's own detector (`src/browser/bot-wall.ts`)
- `pnpm verify:checkout`: six shopper flows on SauceDemo (public practice shop; the harness starts each shopper run signed in (SauceDemo's session cookie, its published test account) and signs in on the login page only for `locked-out`, since jev-browse never lists password fields), a fresh headless Chrome per suite, 3 runs each, recorded into one `report.html`. `place-order` must end `needs_confirmation` on the overview, never on `/checkout-complete.html`; `missing-zip` and `locked-out` expect a hand-back. `JEV_CHECKOUT_RUNS`, `JEV_CHECKOUT_ONLY` narrow it
- `pnpm verify:capabilities`: twelve local tasks in a fresh headless Chrome, 3 runs each: one per README "Limits" gap (a list in a nested scroll pane, infinite scroll in a pane, a link that opens a new tab, an upload through a hidden file input, a same-origin and a cross-origin iframe form), four that must be handed back (a disabled field, a missing option, a 404, a sign-in wall with no values) and two guards (signing in must not stop for confirmation; "Place order" must). The report leads with the false-done count (`done` while `window.__fixture` says otherwise), then guard violations; a task marked `gap` is reported as a known gap until its plan lands. `JEV_CAPABILITIES_RUNS`, `JEV_CAPABILITIES_ONLY` narrow it; `node verify/capabilities.ts --self-check` checks every judge without a model
- `pnpm apps:forgejo:up` then `pnpm verify:forgejo`: eleven write jobs (labelled issue, comment, milestone, branch protection, plus two destructive jobs and one invalid name that must be handed back) on a throwaway Forgejo + Mailpit in Docker (compose project `jev-forgejo`, ports 3311/8325/1325). Each run starts from a reseeded demo and is judged by Forgejo's API. Needs Docker and `TYPESAFE_API_KEY`; `JEV_FORGEJO_RUNS`, `JEV_FORGEJO_ONLY` narrow it; `JEV_FORGEJO_CHECKS=1` passes the caller's `checks` on the five jobs whose ground truth shows on their final page (judging unchanged); `pnpm apps:forgejo:down` removes the stack and its data
- `pnpm verify:signup`: five sign-up jobs on the same Forgejo + Mailpit (sign up and activate through the emailed link, plus a full-name step; a malformed email, a taken username and a password handed over must be handed back). The harness types password fields (jev-browse never lists them) and reads the mail; accounts are named `signup-…`. Judged by Forgejo's admin API. `JEV_SIGNUP_RUNS`, `JEV_SIGNUP_ONLY` narrow it
- `pnpm apps:vikunja:up` then `pnpm verify:vikunja`: eleven jobs (a task, due date, label, done mark, priority, comment, move and a new project; an overdue task to open; a project deletion and a missing project that must be handed back) on a throwaway Vikunja in Docker (compose project `jev-vikunja`, port 3312), signed in as grace, each run from a reseeded demo and judged by Vikunja's API. The held-back app: the job list was frozen before its first run and no rule was tuned on it, so never change a job after a run. `JEV_VIKUNJA_RUNS`, `JEV_VIKUNJA_ONLY` narrow it; `node verify/vikunja.ts --self-check` runs the checks without a model; `pnpm apps:vikunja:down` removes the stack and its data
- `pnpm verify:agent`: Claude Code headless (`claude -p`, `JEV_AGENT_MODEL`, default `sonnet`) is the calling agent, with only jev-browse's `browser_task` and `browser_task_end` over MCP, on eight chores (six on the Forgejo stack above, two read-only in the Langfuse demo through the Chrome on 9333) judged by the app's state, the recorded calls and the final answer. Three of them probe the consent rule (`confirm_irreversible` only for the action and target the request names): a named deletion, a look at the danger zone, a vague "tidy up"; an unnamed repository deleted stops the suite. Each confirm call is reported as honoured or ignored (a flag counts on a session's first call or right after a `needs_confirmation`), with its `confirm_target`, whether the prompt contains it and whether jev-browse matched it; only honoured calls are judged. Spends Claude usage (a run stops at $2, the suite at `JEV_AGENT_BUDGET_USD`, default 15); `JEV_AGENT_RUNS` (default 1), `JEV_AGENT_ONLY` narrow it. Hand-backs are reported per run
- `pnpm mcp` / `pnpm cli -- --help`: run from source (Node ≥24 strips types natively)

## Layout
- `src/browser/`: CDP over the global WebSocket (`cdp.ts`), Chrome connect/launch (`chrome.ts`), guarded tab executor (`tab.ts`), and `snapshot.js` (vendored from jev-ultrafast; keep it diffable)
- `src/jev/`: action space, instructions, `box.ts` (Box answers → viewport rects → observed targets), `decide.ts` (one request: operation + speculative target/value/commit-risk/done-check heads), and `model.ts` (decision model profiles: Jev direct or via OpenRouter, plus Clef, Perplexity and GPT-6 Luna deciders: route, threshold, rules, screenshots, per-element risk)
- `src/task/`: `run-task.ts` loop and hand-back rules (incl. Box stops, rescue, Enter after search typing); `start-task.ts` connects the browser; `recording.ts` writes the optional human record (`recordDir`: screencast `run.mp4` via ffmpeg, step shots, `index.html`)
- `src/journeys/`: journey mapping; `screen-boxes.ts` adds Box primary-action hotspots and missing-from-DOM QA
- `src/mcp.ts`, `src/cli.ts`: entry points; `skill/`: the agent-facing skill; `verify/`: live e2e plus the fixture

## Invariants
- `tab.want(values)`: an off-screen link, button or row containing a supplied value is listed anyway (clicking scrolls it in), so a value the caller found in a table isn't lost below the fold.
- `observe()` waits, up to 1.5 s, while 3 or more on-screen elements with no text run an endless animation (skeleton blocks, spinners), so a page drawn as placeholders isn't read as loaded; if they still pulse at the cap, the page text starts `Loading: N placeholder blocks on screen`.
- Model output only selects observed ids/keys. Never turn it into selectors, coordinates, scripts, or typed text. Box answers are mapped back to observed ids (`matchTarget`). The one exception is opt-in `allowCoordinateClicks`: BLOCKED, a confident box that matches no observed element, a hit-test at its centre, and the commit-risk gate.
- PRESS_ENTER is a fixed key, offered only right after typing into a search-like or filter field, and pressed only while that field still has focus. PRESS_ESCAPE is a fixed key offered only while an observed element is expanded (menu, popover, suggestions).
- Loop guards, generic rather than per site: a target covered by a popup layer (or while something is expanded) gets one automatic `dismissPopup` (Escape to the focused element, then blur and a synthetic outside press on `body`; focus is never moved first, it re-opens search suggestions); a BLOCKED step first opens the collapsed control the click head favours, or else a collapsed overflow control ("+1", "More actions", "⋯"), and the rescues never open the signed-in user's account menu (the model still can); an unsure step (under `minConfidence`, goal not yet accepted by the screenshot check) tries the overflow controls too instead of handing back `uncertain`, count chips ("+1", "Show N more …") first; at most 3 are judged per step, each is opened once per task and judged by name like any click; a target unreachable on an unchanged page is told to Jev on the 2nd miss (naming up to 3 listed controls of the fixed or modal layer covering it) and handed back (`blocked`) on the 3rd; an unsure WAIT still waits and an unsure PRESS_ESCAPE still presses; one action toggling the page A/B 4×, or the same element used 6 times in 7 actions, is `blocked`; a rejected DONE goes into history as "not visible yet" (naming a flipped box that nothing on the page was clicked after to save it, the same way); a risky click elsewhere while a menu this run opened still lists a supplied value (an option row) that was not picked is fed back once per option (pick it first); a click that would flip back a checkbox or switch this run flipped (same path and label, state unchanged since) is fed back once (saying whether anything on the page was clicked after it: if not, save it; if so, DONE if met), then handed back `blocked`; 6 executed actions in a row under 0.5 confidence (waits and Escapes not counted) is `uncertain`; `done_when` ≥ 0.75 on 3 consecutive decisions is `done`; ≥ 0.9 once is `done` too, unless the next step confidently contradicts it (≥ 0.6 on another action, `fallback` screenshots): then one screenshot look must also clear 0.5.
- Escape, Wait, Scroll and Enter refused twice in a row because the page keeps changing run anyway the third time (Enter only while its field has focus); one refusal still waits out an animation. An action refused as stale (the page changed since the decision) does not spend the `maxSteps * 2` decision budget; past 2 × `maxSteps` such refusals in a run it is `blocked` (`GUARDS.staleRefusalsPerStep`).
- TYPE_TEXT types only `values[key]` from the caller. Choosing a field with no fitting value is fed back once (pick another step); the second time it becomes `needs_input`.
- A click that looks irreversible is handed back as `needs_confirmation`; the agent-facing text (tool description, reason, `skill/jev-browse/SKILL.md`) lets the agent set `confirm_irreversible` (one click each, honoured only on the call right after a needs_confirmation or on a new session's first call) only for the action and target the user's own request names, and otherwise tells it to ask the user. The confirmation must carry `confirm_target` (the user's words naming the target), and the click runs only when the page (title, address, visible text or values typed there) shows it. A confirmation that answers a needs_confirmation allows only the control it asked about (same full label, same URL pathname; the query string is ignored, as single-page apps rewrite it): a different risky control is handed back `needs_confirmation` again (the reason still starts `Clicking "<label>"` and names the control that was confirmed), and that spends the confirmation. A new session's first-call confirmation answers no flagged control, so it allows any one risky click whose target the page shows. The control's own words and filler words never count, and at least one other word of 3+ characters must, with all of them shown. A risky submit chosen again on the same form (same path, the typed fields still listed) after the page answered it with new text is handed back `blocked`, quoting that text.
- A call stops when the caller cancels (the MCP request's `signal`, CLI Ctrl-C: `blocked`, "Cancelled by the caller") or when `max_seconds` (default 300, per call) pass (`step_budget`, the reason names the time budget). The run checks before every decision and right before every input (`act`, `clickAt`, each `dismissPopup`); waits end early, and every Jev request (with its SDK retries and Retry-After sleeps) and model screenshot carries or races the stop signal, so neither is ever reported as a model or browser error. An input already under way is never aborted: it finishes, is reported, and nothing runs after it. A session's next call waits for a cancelled call that is still finishing, then runs normally.
- `allowed_hosts` / `blocked_hosts` (exact hosts or `*.example.com`, which excludes the apex) keep a run on the caller's sites. The server's `JEV_ALLOWED_HOSTS` / `JEV_BLOCKED_HOSTS` come first and each later layer (the call, then later calls on the session) can only narrow them: blocked lists add up, and a newer allowed list must lie inside the previous one or the call fails naming the pattern. A start URL outside is never opened; the page URL is checked before every decision and right after every executed step (a click leaves a site as surely as a navigation), and leaving ends the run `blocked` naming the host, without navigating back. `about:blank`, `about:srcdoc` and `chrome-error://` always pass, `blob:` counts as its origin's host, and any other URL without a host is outside an allowed list.
- A click or tap the page never received (no trusted `pointerdown`/`mousedown`/`touchstart` reached a counter registered before the page's scripts) ends the run `blocked` with that reason (`InputNotDelivered`, not a `StalePage`); it is never retried automatically, because a click the page did receive but the counter missed must not run twice.
- A page's native dialog is answered at once with the choice that changes nothing (OK for an alert, Cancel for confirm/prompt, Stay for beforeunload) and reported to Jev on the step that raised it, except a confirm dialog opened by the click the caller confirmed, in that step, whose message names the `confirm_target` words or the clicked control's label, which gets OK (a prompt or beforeunload never does); a declined confirm, prompt or beforeunload that comes back in the same session ends the run `blocked`. A beforeunload after a click on a page with unsaved typed text (or a ticked control) is fed back once as "save first", then handed back naming the field. A protocol call that times out ends the run as a browser error, never a stale page.
- What a page shows right after a risky click, or a click that saves a pending edit (typed or ticked, not yet saved), is put first in the page text Jev reads, as `[Page message after "<label>"] …`: only lines this run never saw on that path, at most 300 characters, kept while the run stays on that path and replaced at the next such click. The done check judges the current page's text only (history is discounted), so a "saved" message that scrolled away needs this line; the caller's `page_text` is unchanged.
- `done` requires the `done_when` Noul ≥ 0.5 when `done_when` is given. A BLOCKED whose `done_when` Noul is ≥ 0.5 is `done` too: nothing is left to do. An unsure next step on a screenshot-backed decision whose `done_when` Noul is ≥ 0.75 is `done` too. Right after an unsaved edit (typed, or a checkbox, radio or switch ticked that is still on the page; no step since) a DONE or BLOCKED needs the done check ≥ 0.75 once. Before ending `done` at any of these, a menu the run itself opened and left open (not a fold the overflow rescue opened to read) is closed once with the fixed Escape and done is judged again on the closed page.
- A bot wall ends the run `blocked`, before a decision is spent on it, with a reason naming it (Cloudflare, reCAPTCHA, hCaptcha, Turnstile, an "unusual traffic" page) and the markers seen, and the summary's `wall: { kind: 'bot_check', origin, name }` (the field a sign-in wall shares as `kind: 'sign_in'`). `src/browser/bot-wall.ts` judges the page alone (no model, no response header): a Cloudflare challenge title with a challenge line, 3+ distinct challenge lines including a brand line (Ray ID, Cloudflare's footer, Google's unusual-traffic sentence), or a visible challenge box ≥ 16000 px² with 2+ lines, all within the title and the first 600 characters of text, so an article or thread that quotes them, or a sign-in page, is not one. A wall gets `wallWaitMs` (8 s) to clear itself, once per call; a `done` is never returned on one (a page changed since the decision is read again first). The run never interacts with a challenge.
- The caller's `checks` (src/task/checks.ts) are evaluated by code on the final page the summary reports, after the loop, and never go into Jev's request: url, title, the reader's visible text (not its own password/loading lines), and listed controls by role and name, never a selector or script. An empty needle fails. A failed check turns `done` into `uncertain`; all passing turn `blocked`/`uncertain` into `done` only on a stop marked overridable (`stop(…, { overridable: true })`: Jev's own BLOCKED or unsure step, a rejected DONE, the covered-target and `stopAfterLastLook` progress guards; every other stop, such as a page error, a repeated dialog, a dropped click, a stale page or a rejected submit, is final by default) and with `done_when` given and the stopping decision's done check ≥ 0.5 made on that same page (≥ 0.75 while an edit is unsaved). `needs_input`, `needs_confirmation`, `step_budget` are never changed. `TaskStatus` is unchanged.
- A `done` with `done_when` carries `evidence: {quote, url, deep_link?, confidence}`: one extra Jev Choice (src/jev/decide.ts `evidenceRequest`) over spans of the final page's visible text that code cut (src/task/evidence.ts, at most 100, then `absent`); code copies the chosen span word for word, never text from the model. `absent`, an answer under 0.5 or a failed request leave it out and never change the status. `deep_link` is a text fragment, left out for a quote under 2 words or 12 characters or shown twice.
- Verification asserts ground truth (`window.__fixture`, URL), never the agent's own status alone.
- Screenshot marks come only from snapshot rects and are removed before any input. The image never yields coordinates.
- `browser_look` (src/task/look.ts) only observes: no Jev request, no input, no node or action ids, rects or guards in what it returns; a `url` look closes its tab again.
- Password fields are never listed; the request carries only whether each visible one is filled or empty (`password_fields`, plus a page-text line), never its value or length.
- A value whose key the caller lists in `secret_keys` (opt-in, kept for the session) reaches Jev only as `[secret:<key>]`, in `supplied_values` and the value question; it is typed as given. The value (as typed, trimmed, URL- or form-encoded, any case) is replaced by that marker in every string of Jev's requests (the whole request, every key, scrubbed where `buildRequest`, each follow-up and the done's evidence request put it together; `image_url` parts and the `Image` asset are left as they are), in summaries (checks and evidence included), `task.trace` and the recording's text (`summary.json`, `index.html`, step descriptions and URLs); recorded screenshots and video are not masked. It is never handed to `tab.want`, so the page's scripts don't see it before it is typed. With no secret key, Jev's request is exactly as before. The loop itself keeps raw values (typing, `value_kept`, resubmit and target checks).
- A `needs_input` summary carries `missing`: one `{ label, role?, path }` per field that wants a value (the field Jev chose, or each empty field a BLOCKED found no value for), `path` being the URL pathname. The reason text is unchanged.
- Recorded (`sharp`) screenshots are for people only and never go into a request.
- Thresholds and rules are tuned per model. Jev's `NEXT_ACTION`, 0.3 and page-level commit risk are its verified baseline, so don't retune them on other models' data. Jev's chosen click is also judged by name (`pageRisk`), and it is risky if either question says so (a collapsed control, `expanded=false`, or an option picked from an open list, is judged by name only). The loop guards in `GUARDS` (run-task.ts) are Jev-only provisional baselines.
