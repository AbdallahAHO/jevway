# jevway

MCP server + CLI that hands browser goals to TypeSafe Jev (one `/v1/systemone` decision request per step, plus follow-ups such as the per-click commit-risk question) and returns a short summary to the calling agent.

Humans start at [CONTRIBUTING.md](CONTRIBUTING.md); how a step works end to end is in [docs/how-it-works.md](docs/how-it-works.md). This file is the short form: commands, layout and the rules the code must keep.

## Commands

### Everyday
- `pnpm test`: offline unit tests (vitest), no key needed
- `pnpm typecheck` / `pnpm build` (emits `dist/`, copies `snapshot.js`)
- `pnpm release:check`: the gate CI runs (typecheck, test, build, `npm pack --dry-run`)
- `pnpm mcp` / `pnpm cli --help`: run from source (Node ≥24 strips types natively); both load `.env`
- `pnpm cli doctor [--plan | --json]`: setup check (key and route, browser, Node, ffmpeg); never prints a key. `--live` makes one real Jev request, so never run it in tests
- `pnpm cli setup`: the interactive setup (terminal only); `pnpm cli setup --client <name> --print [--json]` prints a client's registration and changes nothing; `pnpm cli skill [--install <dir>]` prints or copies the skill

### Live suites
Each spends credits and needs a key in `.env`; the full description of each (jobs, env vars that narrow it, how it is judged) is in [docs/verification.md](docs/verification.md#suites).
- `pnpm verify` (core scenarios, about 30 s), `verify:reader` (no model), `verify:gotchas`, `verify:redteam`, `verify:capabilities`
- `verify:forgejo`, `verify:signup`, `verify:vikunja` (Docker: `pnpm apps:forgejo:up`, `pnpm apps:vikunja:up`; `:down` removes the stack and its data)
- `verify:checkout`, `verify:real`, `verify:langfuse`, `verify:grafana` (Langfuse and Grafana need a signed-in Chrome on a debugging port)
- `verify:agent` (a real calling agent over MCP; spends that agent's usage too), `verify:journeys`
- `pnpm verify:replay [--record] <dir>`: record Jev's answers once, replay the fixture suites offline with no key
- `pnpm report:render <verify/out/folder>`: rebuild a suite's `report.html` or a run's `index.html`, offline
- Vikunja is the held-back app for R6: never change a job after a run. The next release gate needs a new held-back app

### CI and releases
- CI: `.github/workflows/ci.yml` runs `pnpm release:check` on every PR and push to `main`
- Releases: release-please (`.github/workflows/release.yml`) keeps one release PR open from the conventional commits on `main`; merging it tags `v<version>`, writes `CHANGELOG.md` and publishes to npm through trusted publishing (OIDC, no token; `prepublishOnly` typechecks, tests and rebuilds `dist/`). Below 1.0, `feat:` and breaking changes bump the minor and `fix:`/`perf:` the patch; `docs:`, `test:`, `chore:` and `refactor:` release nothing. Never bump `version` by hand: release-please bumps `package.json`, `.release-please-manifest.json` and both `.claude-plugin/` manifests together (`test/package.test.ts` checks). Never run `npm publish` locally: the package disallows tokens and CI publishes
  - `pnpm release:status`: main, npm, CI and the release PR, plus the one next step (read-only; `node release/release.ts status --json` for scripts)
  - `pnpm release`: merges the release PR once CI is green on main, watches the release workflow and waits until npm lists the version; asks first, `--yes` skips the question (required without a terminal)
  - `pnpm release as <x.y.z>`: forces a version when nothing releasable landed (empty `Release-As:` commit pushed to main, then the same flow); needs a clean, up-to-date `main`
  - `pnpm release:check`: the publish gate locally (typecheck, test, build, `npm pack --dry-run`)
  - Tests must pass without a key: stub `TYPESAFE_API_KEY` in tests that start a runner (CI has none)

## Layout
- `src/browser/`: CDP over the global WebSocket (`cdp.ts`), Chrome connect/launch (`chrome.ts`), guarded tab executor (`tab.ts`), frames (`frames.ts`: finds same-process and out-of-process frames, reads each in an isolated world, places and merges them), and `snapshot.js` (vendored from jev-ultrafast; keep it diffable)
- `src/jev/`: action space, instructions, `box.ts` (Box answers → viewport rects → observed targets), `decide.ts` (one request: operation + speculative target/value/commit-risk/done-check heads), and `model.ts` (decision model profiles: Jev direct or via OpenRouter, plus Clef, Perplexity and GPT-6 Luna deciders: route, threshold, rules, screenshots, per-element risk; and the input price per model id behind a summary's `jev.est_cost_usd`, listed only where a rate is written down, otherwise null)
- `src/task/`: `run-task.ts` loop and hand-back rules (incl. Box stops, rescue, Enter after search typing); `start-task.ts` connects the browser; `checks.ts`, `evidence.ts`, `hosts.ts`, `look.ts` are the caller-facing extras; `present.ts` turns a summary into what the caller reads (`story`, `next`, concise or full)
- `src/session/`: `session-service.ts`, the transport-free sessions and journeys (UUID ids, folders, waiting on a running call, step events, `UnknownSession`) that the MCP server and the CLI daemon adapt
- `src/output/`: the output root (`./.jevway` or `JEVWAY_OUT_DIR`, with a `.gitignore` of `*`), folder and file names and slugs (`layout.ts`), `manifest.json` (`manifest.ts`), and what a call leaves in its run folder (`run-folder.ts`: `final.jpg`, `calls/NN-<status>.jpg`, `summary.json`)
- `src/recording/`: `recording.ts` writes the optional human record (`output.record`, or `recordDir`: screencast `run.mp4` via ffmpeg, `steps/NN-<what>.jpg` shots, `summary.json` with the `viewport`, `index.html`) and holds `describeStep`, the step wording the run page and a summary's `story` share; `recording-page.ts` is the design all recording pages share (tokens, grid, the synced player) with `verify/jobs/report-page.ts` and `verify/agent/report.ts`
- `src/journeys/`: journey mapping; `screen-boxes.ts` adds Box primary-action hotspots and missing-from-DOM QA
- `src/mcp.ts`, `src/cli.ts`: entry points; `src/setup/`: `~/.config/jevway/env` loading (fills only unset keys, `CHROME_PATH` and `JEVWAY_*`) and writing (`setEnvValue`, mode 600), `jevway doctor`, `jevway setup` (`clients.ts`: each MCP client's detection, registration and skills folder; `setup-wizard.ts`: the interactive steps behind an injected `Prompter`; `unified-diff.ts`), and `jevway skill`; `.claude-plugin/`: the Claude Code plugin (npx server + `skill/jevway`); `skill/`: the agent-facing skill; `verify/`: live e2e plus the fixture; `verify/jobs/`: the shared jobs runner and its report (`report.ts` markup, `report-page.ts` style and script, `rerender.ts`)
- `release/`: `state.ts` decides the next release step from main, npm, CI and the release PR (pure, tested in `test/release/release.test.ts`); `release.ts` is the `pnpm release*` CLI over `gh`, `git` and `npm`

## Invariants

A **Noul** is a yes/no question in a Jev request; its answer is a probability from 0 to 1. Each rule below is explained in [docs/how-it-works.md](docs/how-it-works.md).

### What the model may decide
The core contract: model output selects; code types, clicks and checks.
- Model output only selects observed ids/keys. Never turn it into selectors, coordinates, scripts, or typed text. Box answers are mapped back to observed ids (`matchTarget`). The one exception is opt-in `allowCoordinateClicks`: BLOCKED, a confident box that matches no observed element, a hit-test at its centre, and the commit-risk gate.
- TYPE_TEXT types only `values[key]` from the caller. Choosing a field with no fitting value is fed back once (pick another step); the second time it becomes `needs_input`.
- UPLOAD sets only a file the caller declared in `files` (key → absolute path, checked to be a readable file before the run; never from `values`, never from the model), with `DOM.setFileInputFiles` after the element-level freshness check. File inputs are listed and UPLOAD offered only when files are declared, so a call without them sends Jev the same request as before. The request carries each key and file name (`supplied_files`, `file_for_<index>`), never a path. No fitting file is fed back once, then `needs_input`.
- Screenshot marks come only from snapshot rects and are removed before any input. The image never yields coordinates.
- Password fields are never listed; the request carries only whether each visible one is filled or empty (`password_fields`, plus a page-text line), never its value or length.
- A value whose key the caller lists in `secret_keys` (opt-in, kept for the session) reaches Jev only as `[secret:<key>]`, in `supplied_values` and the value question; it is typed as given. The value (as typed, trimmed, URL- or form-encoded, any case) is replaced by that marker in every string of Jev's requests (the whole request, every key, scrubbed where `buildRequest`, each follow-up and the done's evidence request put it together, and before that every page the run reads is scrubbed as `observe()` returns it (title, URL, text, labels, field values, password field names; not the marker, guards or a select option's value), so nothing built from it and then cut short (history labels, descriptions, `page_text`) can hold a cut secret; `image_url` parts and the `Image` asset are left as they are), in summaries (checks and evidence included), `task.trace`, the story and step events, and the run folder's text (`summary.json`, `index.html`, `manifest.json`, step descriptions and URLs) and file and folder names (a slug is made from scrubbed text and scrubbed again); recorded screenshots, `final.jpg` and video are not masked. It is never handed to `tab.want`, so the page's scripts don't see it before it is typed. With no secret key, Jev's request is exactly as before. The loop itself keeps raw values (typing, `value_kept`, resubmit and target checks).
- Recorded (`sharp`) screenshots are for people only and never go into a request.
- Thresholds and rules are tuned per model. Jev's `NEXT_ACTION`, 0.3 and page-level commit risk are its verified baseline, so don't retune them on other models' data. Jev's chosen click is also judged by name (`pageRisk`), and it is risky if either question says so (a collapsed control, `expanded=false`, or an option picked from an open list, is judged by name only). The loop guards in `GUARDS` (run-task.ts) are Jev-only provisional baselines.

### Reading the page
- `tab.want(values)`: an off-screen link, button or row containing a supplied value is listed anyway (clicking scrolls it in), so a value the caller found in a table isn't lost below the fold.
- `observe()` waits, up to 1.5 s, while 3 or more on-screen elements with no text run an endless animation (skeleton blocks, spinners), so a page drawn as placeholders isn't read as loaded; if they still pulse at the cap, the page text starts `Loading: N placeholder blocks on screen`.
- SCROLL_DOWN/SCROLL_UP keep today's action on a page whose document can move that way. When it can't, they are offered for the largest visible pane that can (overflow `auto`/`scroll`/`overlay`, at least 50×50 px visible), with the wheel at the centre of its visible part (DOM rects only) and a step of 80 % of that height (100–560 px). Each scroll measures the page's scroll offsets before and after; one that moved nothing goes into history as `Scroll down (nothing moved: there is no more to scroll this way)`.
- Frames are read with the same `snapshot.js`, each in an isolated world `jevway` (the main frame keeps the main world). Each frame owns an id range (`FRAME_ID_STRIDE`; main is 0), so ids are unique and stable and every node routes to its frame. A frame action's rect is in viewport pixels (owner content-box offsets compound; the frame's visible part is clipped by every parent), and it is listed only where every document around the frame has the frame on top. Freshness, the cover check (plus a parent hop that names the covering layer's ids), the input counter (registered in the frame's world before its scripts, out-of-process frames held at start until then), `SETTLE`, Enter and hover all run in the target's frame; before a press into a frame, two animation frames are awaited there (an unpainted frame lets the press fall through). Page-level actions compare frames by document (start time, URL), not text. Frame text (only what shows in the frame's visible part) follows the main text under `[Frame: …]`, frames keeping at least 1000 of the 6000 characters; password lines of every frame come first (5 at most). A frame read that fails or exceeds 1.5 s is skipped, never a browser error; acting in a frame keeps the timeout rule. Native dialogs from any frame reach the page session's handler.
- `jevway_look` (src/task/look.ts) only observes: no Jev request, no input, no node or action ids, rects or guards in what it returns; a `url` look closes its tab again.

### Acting and loop guards
- PRESS_ENTER is a fixed key, offered only right after typing into a search-like or filter field, and pressed only while that field still has focus. PRESS_ESCAPE is a fixed key offered only while an observed element is expanded (menu, popover, suggestions).
- Loop guards, generic rather than per site: a target covered by a popup layer (or while something is expanded) gets one automatic `dismissPopup` (Escape to the focused element, then blur and a synthetic outside press on `body`; focus is never moved first, it re-opens search suggestions); a BLOCKED step first opens the collapsed control the click head favours, or else a collapsed overflow control ("+1", "More actions", "⋯"), and the rescues never open the signed-in user's account menu (the model still can); an unsure step (under `minConfidence`, goal not yet accepted by the screenshot check) tries the overflow controls too instead of handing back `uncertain`, count chips ("+1", "Show N more …") first; at most 3 are judged per step, each is opened once per task and judged by name like any click; a target unreachable on an unchanged page is told to Jev on the 2nd miss (naming up to 3 listed controls of the fixed or modal layer covering it) and handed back (`blocked`) on the 3rd; an unsure WAIT still waits and an unsure PRESS_ESCAPE still presses; one action toggling the page A/B 4×, or the same element used 6 times in 7 actions, is `blocked`; a rejected DONE goes into history as "not visible yet" (naming a flipped box that nothing on the page was clicked after to save it, the same way); a risky click elsewhere while a menu this run opened still lists a supplied value (an option row) that was not picked is fed back once per option (pick it first); a click that would flip back a checkbox or switch this run flipped (same path and label, state unchanged since) is fed back once (saying whether anything on the page was clicked after it: if not, save it; if so, DONE if met), then handed back `blocked`; 6 executed actions in a row under 0.5 confidence (waits and Escapes not counted) is `uncertain`; `done_when` ≥ 0.75 on 3 consecutive decisions is `done`; ≥ 0.9 once is `done` too, unless the next step confidently contradicts it (≥ 0.6 on another action, `fallback` screenshots): then one screenshot look must also clear 0.5.
- Escape, Wait, Scroll and Enter refused twice in a row because the page keeps changing run anyway the third time (Enter only while its field has focus); one refusal still waits out an animation. An action refused as stale (the page changed since the decision) does not spend the `maxSteps * 2` decision budget; past 2 × `maxSteps` such refusals in a run it is `blocked` (`GUARDS.staleRefusalsPerStep`).
- A click or tap the page never received (no trusted `pointerdown`/`mousedown`/`touchstart` reached a counter registered before the page's scripts) ends the run `blocked` with that reason (`InputNotDelivered`, not a `StalePage`); it is never retried automatically, because a click the page did receive but the counter missed must not run twice. On a followed tab (one the session's tab opened) the counter is installed shortly after the tab appears, not before its first document's scripts: a page listener registered in that window that hides a press makes a delivered click read as dropped, which ends the run `blocked` the same way.
- A page's native dialog is answered at once with the choice that changes nothing (OK for an alert, Cancel for confirm/prompt, Stay for beforeunload) and reported to Jev on the step that raised it, except a confirm dialog opened by the click the caller confirmed, in that step, whose message names the `confirm_target` words or the clicked control's label, which gets OK (a prompt or beforeunload never does); a declined confirm, prompt or beforeunload that comes back in the same session ends the run `blocked`. A beforeunload after a click on a page with unsaved typed text (or a ticked control) is fed back once as "save first", then handed back naming the field. On a followed tab, dialogs are answered only once it is set up (shortly after it appears): one it raised before that freezes it, `Page.enable` does not re-send it, and following it fails after 5 s as a browser error (`blocked`), leaving that tab open. A protocol call that times out ends the run as a browser error, never a stale page.
- What a page shows right after a risky click, or a click that saves a pending edit (typed or ticked, not yet saved), is put first in the page text Jev reads, as `[Page message after "<label>"] …`: only lines this run never saw on that path, at most 300 characters, kept while the run stays on that path and replaced at the next such click. The done check judges the current page's text only (history is discounted), so a "saved" message that scrolled away needs this line; the caller's `page_text` is unchanged.
- A tab the session's tab opens (`Target.targetCreated` whose `openerId` is that tab) becomes the session's tab, newest first; nothing else discovery reports is attached, read or closed (the user's tabs in `auto` mode). It gets `Tab.attach`'s setup plus the opener's device, wanted values and confirm arm when it is followed, which can be after its first document's scripts (no browser-level `waitForDebuggerOnStart`: it would pause the user's tabs). The step that opened it gains `(new tab opened: <url>)`; a closed tab falls back to the newest open one with `(the tab closed; back on <url>)`. Confirmation state is the task's, so it carries over. `closeTabs` closes every followed tab, and the first only when the session opened it.

### Hand-backs and statuses
- A click that looks irreversible is handed back as `needs_confirmation`; the agent-facing text (tool description, reason, `skill/jevway/SKILL.md`) lets the agent set `confirm_irreversible` (one click each, honoured only on the call right after a needs_confirmation or on a new session's first call) only for the action and target the user's own request names, and otherwise tells it to ask the user. The confirmation must carry `confirm_target` (the user's words naming the target), and the click runs only when the page (title, address, visible text or values typed there) shows it. A confirmation that answers a needs_confirmation allows only the control it asked about (same full label, same URL pathname; the query string is ignored, as single-page apps rewrite it): a different risky control is handed back `needs_confirmation` again (the reason still starts `Clicking "<label>"` and names the control that was confirmed), and that spends the confirmation. A new session's first-call confirmation answers no flagged control, so it allows any one risky click whose target the page shows. The control's own words and filler words never count, and at least one other word of 3+ characters must, with all of them shown. A risky submit chosen again on the same form (same path, the typed fields still listed) after the page answered it with new text is handed back `blocked`, quoting that text.
- A call stops when the caller cancels (the MCP request's `signal`, CLI Ctrl-C: `blocked`, "Cancelled by the caller") or when `max_seconds` (default 300, per call) pass (`step_budget`, the reason names the time budget). The run checks before every decision and right before every input (`act`, `clickAt`, each `dismissPopup`); waits end early (the bot-wall wait, and the tab's own: a followed tab's address and load, a scroll's settle poll after its wheel, frame reads), and every Jev request (with its SDK retries and Retry-After sleeps, the done's evidence request too) and model screenshot carries or races the stop signal, so neither is ever reported as a model or browser error. An input already under way is never aborted: it finishes, is reported, and nothing runs after it. A session's next call waits for a cancelled call that is still finishing, then runs normally.
- `allowed_hosts` / `blocked_hosts` (exact hosts or `*.example.com`, which excludes the apex) keep a run on the caller's sites. The server's `JEVWAY_ALLOWED_HOSTS` / `JEVWAY_BLOCKED_HOSTS` come first and each later layer (the call, then later calls on the session) can only narrow them: blocked lists add up, and a newer allowed list must lie inside the previous one or the call fails naming the pattern. A start URL outside is never opened; the page URL is checked before every decision and right after every executed step (a click leaves a site as surely as a navigation), and leaving ends the run `blocked` naming the host, without navigating back. `about:blank`, `about:srcdoc` and `chrome-error://` always pass, `blob:` counts as its origin's host, and any other URL without a host is outside an allowed list.
- Every step request asks two yes/no questions: does the page show an error caused by the actions so far (`page_error`), and is it a sign-in screen blocking the goal (`sign_in_wall`). An error at or above `PAGE_ERROR_STOP`, after this call executed an action, ends the run `blocked` quoting the page message, else the lines the last action brought (lines not on the page before it); with neither there is no quote and no stop. A sign-in wall at or above `SIGN_IN_WALL_STOP` ends it `blocked` with `wall: { kind: 'sign_in', origin }` only when the page has an empty field (text or password) and no supplied value fits any empty text field; a page whose fields are all filled never stops. Both checks run after the done checks, so a met condition wins. The thresholds were set from recorded scores (plans/103).
- `done` requires the `done_when` Noul ≥ 0.5 when `done_when` is given. A BLOCKED whose `done_when` Noul is ≥ 0.5 is `done` too: nothing is left to do. An unsure next step on a screenshot-backed decision whose `done_when` Noul is ≥ 0.75 is `done` too. Right after an unsaved edit (typed, or a checkbox, radio or switch ticked that is still on the page; no step since) a DONE or BLOCKED needs the done check ≥ 0.75 once. Before ending `done` at any of these, a menu the run itself opened and left open (not a fold the overflow rescue opened to read) is closed once with the fixed Escape and done is judged again on the closed page.
- A bot wall ends the run `blocked`, before a decision is spent on it, with a reason naming it (Cloudflare, reCAPTCHA, hCaptcha, Turnstile, an "unusual traffic" page) and the markers seen, and the summary's `wall: { kind: 'bot_check', origin, name }` (the field a sign-in wall shares as `kind: 'sign_in'`). `src/browser/bot-wall.ts` judges the page alone (no model, no response header): a Cloudflare challenge title with a challenge line, 3+ distinct challenge lines including a brand line (Ray ID, Cloudflare's footer, Google's unusual-traffic sentence), or a visible challenge box ≥ 16000 px² with 2+ lines, all within the title and the first 600 characters of text, so an article or thread that quotes them, or a sign-in page, is not one. A wall gets `wallWaitMs` (8 s) to clear itself, once per call; a `done` is never returned on one (a page changed since the decision is read again first). The run never interacts with a challenge.
- Every step request also asks whether the run is stuck (`stuck`, with true/false meanings); the score is recorded in the trace only, and no guard, status or reason reads it (plans/105).
- A `needs_input` summary carries `missing`: one `{ label, role?, path }` per field that wants a value (the field Jev chose, or each empty field a BLOCKED found no value for), `path` being the URL pathname. The reason text is unchanged.

### Finishing: checks and evidence
- The caller's `checks` (src/task/checks.ts) are evaluated by code on the final page the summary reports, after the loop, and never go into Jev's request: url, title, the reader's visible text (not its own password/loading lines), and listed controls by role and name, never a selector or script. An empty needle fails. A failed check turns `done` into `uncertain`; all passing turn `blocked`/`uncertain` into `done` only on a stop marked overridable (`stop(…, { overridable: true })`: Jev's own BLOCKED or unsure step, a rejected DONE, the covered-target and `stopAfterLastLook` progress guards; every other stop, such as a page error, a repeated dialog, a dropped click, a stale page or a rejected submit, is final by default) and with `done_when` given and the stopping decision's done check ≥ 0.5 made on that same page (≥ 0.75 while an edit is unsaved). `needs_input`, `needs_confirmation`, `step_budget` are never changed. `TaskStatus` is unchanged.
- A `done` with `done_when` carries `evidence: {quote, url, deep_link?, confidence}`: one extra Jev Choice (src/jev/decide.ts `evidenceRequest`) over spans of the final page's visible text that code cut (src/task/evidence.ts, at most 100, then `absent`); code copies the chosen span word for word, never text from the model. `absent`, an answer under 0.6 or a failed request leave it out and never change the status. `deep_link` is a text fragment, left out for a quote under 2 words or 12 characters or shown twice.

### Sessions and output
- Session and journey ids are a full `randomUUID()`. A call on a session waits for that session's still-running call (a cancelled one finishing its input), then `update()`s and runs. Start-only fields (`url`, `tab`, `allowCoordinateClicks`, the recording) are ignored on a continue. An unknown id is `UnknownSession` (`code: 'unknown_session'`), saying sessions end at a restart (or after the idle time) and to start a new one with `url`.
- A `BrowserTask` without `output` writes nothing. With it, every call writes its end page, `summary.json` and `manifest.json`; writing them, like the recording, never changes or hangs the outcome, and a failed capture leaves the screenshot out rather than showing an older call's page.
- `onStep` / `onEvent` listeners only hear: one that throws is ignored and never decides how the run goes.

### Setup and verification
- `jevway-mcp` runs on MCP SDK v2 through `serveStdio(createServer)`, which serves both protocol eras on stdio: 2025-era clients that open with `initialize` (2024-10-07 to 2025-11-25) and 2026-07-28 clients that send `server/discover` or a per-request `_meta` version. Never connect with `server.connect(new StdioServerTransport())` (2025 clients only). `createServer` may run twice per connection, so it only builds the server; sessions and the runner stay at module level. `@modelcontextprotocol/client` is a dev dependency (tests, `verify/`).
- Without the chosen model's key, `jevway-mcp` still starts and lists every tool: `jevway_look` works (no model call), and `jevway_task` and the journey tools answer `isError` naming the key, `~/.config/jevway/env` and `jevway doctor`, before any browser connects. The CLI reports it as a usage error (exit 2).
- `jevway setup` writes a file only on an explicit yes (the key and browser lines once entered), always whole (temporary file, then rename), the env file with mode 600; it never edits another server's entry or a config file that is not plain JSON, never prints the key, and without a TTY exits 2 asking nothing.
- Verification asserts ground truth (`window.__fixture`, URL), never the agent's own status alone.
